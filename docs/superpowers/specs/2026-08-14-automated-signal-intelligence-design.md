# 自动化信号情报系统设计

## 1. 目标与范围

在现有“信号雷达｜主题研判｜基金产品库”完整工作台上，将静态演示信号升级为可持续运行的自动情报系统。系统每小时采集公开信息，每天北京时间 08:00 生成《决策信号日报》，统计窗口为前一日 08:00 至当日 08:00。

第一阶段不依赖付费大模型 API，以规则引擎、结构化数据和免费基础设施完成采集、去重、分类、评分、异常识别和日报生成。大模型能力保留为可选增强接口，缺少密钥时不得阻断更新。

系统服务于中国公募基金产品经理，目标不是生成交易指令，而是回答：市场与政策发生了什么、客户需要什么、哪些产品机会值得进一步研究、哪些证据仍不足。

## 2. 信息来源与边界

### 2.1 中国来源为主体

- S 级（基础权重 1.00）：国务院政策文件库、中国人民银行、中国证监会、国家统计局、财政部、国家发展改革委、国家金融监督管理总局。
- A 级（基础权重 0.85）：上交所、深交所、北交所、中证指数、基金业协会等交易所、指数公司和行业协会。
- B/C 级（基础权重 0.20–0.50）：主流财经媒体、其他公开新闻与普通网络信息，只用于事件发现、交叉验证和热度观测。

### 2.2 海外来源只覆盖中国基金配置相关因素

- 美联储：利率决议、会议纪要、经济预测、流动性和资产负债表。
- 美国劳工统计局：通胀、就业和工资数据。
- 欧洲央行：政策利率、货币政策声明和欧元区流动性。
- 国际清算银行：全球流动性、跨境信贷和金融稳定。

海外信息只有在能明确映射到人民币汇率、国内流动性、风险偏好、黄金、债券、QDII 或其他中国公募基金配置时才进入核心信号。

## 3. 客户需求权重

客户需求是业务优先级的核心，但必须把真实需求和代理指标分开：

| 客户需求证据 | 业务权重 | 证据置信度 |
|---|---:|---:|
| 真实申赎、保有量、渠道订单 | 1.00 | 高 |
| 销售访谈、客服工单、正式问卷 | 0.90 | 中高 |
| 渠道搜索、页面点击、收藏、咨询 | 0.75 | 中 |
| 基金份额变化、搜索指数 | 0.50 | 中低（代理） |
| 新闻、自媒体讨论 | 0.20 | 低 |
| 非官方信息异常异增 | 最高 0.60 | 待官方验证 |

真实客户数据可以形成高权重需求信号。代理变量不能冒充真实客户偏好；即使异常升温，也必须显示“待验证”。

## 4. 采集与处理流水线

### 4.1 每小时任务

1. 从 RSS、ICS、公开 API 和允许访问的公开网页采集新增内容。
2. 保存原始标题、正文、链接、发布时间、抓取时间和内容哈希。
3. 通过 URL 规范化、内容哈希、标题相似度和实体组合进行去重与事件聚类。
4. 按政策、宏观、市场、客户需求或客户代理分类。
5. 提取受影响资产、基金类别、主题关键词、方向、时间跨度和失效条件。
6. 计算评分并执行时效衰减。
7. 更新信号、证据、来源健康和未来催化剂。

### 4.2 每日 08:00 任务

汇总前一日 08:00 至当日 08:00 的新增和变化，生成：

1. 今日 Top Call。
2. 过去 24 小时政策、宏观、市场和客户需求核心信号。
3. 非官方信息异常升温主题。
4. 反向证据、来源冲突和待官方验证事项。
5. 今日及未来 7 日催化剂。
6. 受影响基金类别、主题研判和产品库搜索关键词。
7. 抓取失败、缺失数据和质量说明。

日报保持两分钟内可读，结论先行，不以新闻堆砌代替判断。

## 5. 评分与异常检测

### 5.1 分层评分

系统分别保存以下分数，不将“来源权威”和“客户价值”混成一个不可解释的数字：

- `source_confidence`：来源权威度和正文完整性。
- `independence_score`：独立来源数量，转载不重复加分。
- `anomaly_score`：当前事件数量相对历史基线的偏离程度。
- `recency_score`：发布时间、观察时间和有效期衰减。
- `customer_demand_score`：客户需求证据等级与强度。
- `product_relevance_score`：与基金资产、主题和产品机制的相关性。

决策优先级采用可配置组合：

`priority = evidence_confidence × customer_demand × product_relevance × recency`

其中 `evidence_confidence` 由来源权威度、独立来源和正文完整性构成。界面必须展示评分贡献项。

### 5.2 非官方信息异常升级

- 以同一主题的历史滚动基线计算数量偏离，基线窗口第一阶段为 30 天。
- 只有独立来源计入异常数量；转载、镜像和同集团重复发布合并处理。
- 异常至少同时满足“数量偏离”和“独立来源数”阈值。
- 非官方信息异常最多升级为高热度、待官方验证，不能直接成为高置信度政策事实。
- 官方澄清、反向数据或事件降温出现后，系统更新方向和置信度，而不是删除历史记录。

具体阈值存放在配置表，初始值由历史回放测试校准，不硬编码在前端。

## 6. 数据模型

使用 Supabase PostgreSQL：

- `sources`：来源、等级、官方属性、采集方式、基础权重和健康状态。
- `raw_items`：原始内容、链接、发布时间、抓取时间、哈希和解析状态。
- `event_clusters`：事件聚类、规范标题、主题、实体和独立来源数。
- `signals`：分类、方向、期限、各评分项、优先级、状态和有效期。
- `signal_evidence`：信号与支持证据、反向证据的关系。
- `catalysts`：未来事件、预定时间、影响等级、实际结果和复盘。
- `daily_briefs`：日报窗口、正文、Top Call 和生成状态。
- `pipeline_runs`：任务运行、来源成功/失败数、错误和耗时。

原始内容与结构化信号分层保存，保证可追溯和可重新计算。Supabase 使用行级安全策略：浏览器只能读取已发布信号和日报；写入只允许 GitHub Actions 使用服务端密钥。

## 7. 技术组合与调度

- Supabase 免费版：持久化历史数据、查询 API 和权限控制。
- GitHub Actions：每小时运行采集流水线，并在北京时间 08:00 运行日报任务。
- Vercel：继续托管前端，不承担小时级调度。
- 现有 Python 数据管道：复用 SQLite 领域模型、原始快照、质量事件和采集器，并增加 PostgreSQL 仓储适配层。

如仓库为私有仓库，小时任务必须控制运行时间并监测 GitHub Actions 免费分钟；必要时将夜间频率降为两小时一次，但日报窗口和 08:00 生成时间不变。公开仓库可使用标准 runner 的免费额度。

## 8. 前端设计

在现有信号雷达中增加：

- 最后成功更新时间、成功来源数、失败来源数和当前快照状态。
- 更高密度信号流，使用分页或“加载更多”，不一次渲染全部记录。
- 官方、行业机构、媒体、真实客户需求、客户代理等来源徽标。
- 评分解释与贡献项。
- 异常热度，包括当前数量、历史基线、偏离倍数和独立来源数。
- “客户需求”筛选，明确区分真实需求和代理需求。
- 今日决策信号日报入口。
- 未来 7 日催化剂入口。
- 现有详情抽屉继续展示事实、Agent 解读、传导链、反向证据、失效条件、原始链接和观察池操作。

主题研判与基金产品库接口不变。信号可以通过主题 ID 和基金搜索关键词跳转，但不能直接把低置信度热度转换为产品立项结论。

## 9. 失败处理与数据质量

- 单个来源失败不阻断整批更新；连续三次失败标记来源异常。
- 官方正文抓取失败时只保存标题，不生成高置信度解读。
- 无法判断来源是否独立时按转载处理，不增加异常计数。
- 无法分类的内容进入待观察池，不强行生成投资信号。
- Supabase 或任务失败时，前端继续显示最近一次成功快照并明确标注时间。
- 所有自动解读保留事实与推断边界，不构成投资建议。
- 抓取遵守来源站点公开访问规则；禁止绕过登录、验证码、付费墙或访问控制。

## 10. 测试与验收

测试覆盖：

- RSS、ICS、HTML 和结构化接口解析。
- URL、哈希、标题和实体级去重聚类。
- 来源分级、客户需求分级和评分贡献。
- 30 日历史基线与异常升级上限。
- 北京时区、小时任务及 08:00 日报窗口。
- 来源失败、正文缺失、数据库失败和旧快照降级。
- Supabase 行级安全和服务端写入权限。
- 信号分页、筛选、日报、催化剂、详情抽屉与跨工作区跳转。

验收标准：

- 每小时任务可重复执行，重复内容不会产生重复信号。
- 日报只纳入正确的 24 小时窗口，并在无重大信息时明确说明。
- 非官方异常信息不会被标记为官方事实。
- 真实客户需求信号在同等证据条件下优先级高于普通媒体热度。
- 任一单独来源失败时，其他来源仍可更新，前端可看到来源健康状态。
- 所有已发布信号均可追溯到至少一个原始来源。

## 11. 分阶段交付

1. 数据库模式、仓储适配、来源目录与任务运行记录。
2. 中国 S/A 级官方来源、核心海外官方 RSS/日历和催化剂。
3. 去重聚类、评分、客户需求分级与异常检测。
4. 日报生成和前端信号流扩充。
5. 非官方新闻源、历史回放校准和可选大模型增强接口。

第一阶段不接入付费大模型、不绕过来源访问限制、不将媒体热度自动解释为真实客户需求。
