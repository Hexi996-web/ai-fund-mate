# 基金产品与份额模型设计

## 目标

将当前按基金代码展示的基金份额库升级为“基金产品—基金份额”两层结构。页面默认按基金产品展示，用户展开产品后查看 A、C、E、Y、币种等独立份额，同时保留按任一六位代码搜索和定位的能力。

本次改造解决两个问题：

1. 页面基金数量与基金业协会产品统计口径差异过大。
2. 同一产品的多个份额当前被平铺展示，难以比较费率、净值与申赎状态。

## 范围

### 包含

- 为每条活跃基金份额生成 `productId`、`productName`、`shareClass`、`groupingConfidence` 和 `groupingRule`。
- 生成产品级集合，并将全部份额嵌套在 `shares[]` 中。
- 默认按产品展示，支持展开份额。
- 同时显示基金产品数和基金份额数。
- 搜索产品名称、产品 ID、份额名称和份额代码。
- 保持现有份额 JSON 字段兼容，避免旧缓存与旧页面立即失效。
- 输出低置信度待核验清单和归并质量统计。

### 不包含

- 本阶段不以名称规则替代官方基金主标识。
- 不合并 ETF 与 ETF 联接、普通与发起式、不同定开周期、不同对冲策略等经济属性不同的产品。
- 不因为缺少当日涨跌幅而剔除基金。
- 不在本阶段引入付费数据源。

## 数据模型

### 份额记录

现有 `funds_active.json` 中每条份额保留原字段并增量加入：

```json
{
  "code": "000001",
  "name": "示例基金A",
  "productId": "prd_<stable-hash>",
  "productName": "示例基金",
  "shareClass": "A",
  "groupingConfidence": "high",
  "groupingRule": "explicit_share_suffix"
}
```

`productId` 必须由稳定、版本化的规范化键生成，不能使用数组位置或每日随机值。同一规范化键在不同更新日期得到相同 ID。

`shareClass` 使用结构化值，第一版支持：

- `A`、`B`、`C`、`D`、`E`、`F`、`H`、`I`、`R`、`Y` 等明确字母份额；
- `RMB`、`USD_SPOT`、`USD_CASH` 等明确币种份额；
- `DEFAULT`：没有明确份额后缀；
- `UNKNOWN`：存在疑似后缀但规则不能可靠判断。

### 产品记录

新增 `public/fund_products.json`：

```json
{
  "updateTime": "2026-08-13 19:00:00",
  "productTotal": 13821,
  "shareTotal": 24337,
  "groupingVersion": "v1",
  "products": [
    {
      "productId": "prd_<stable-hash>",
      "productName": "示例基金",
      "type": "混合型",
      "representativeCode": "000001",
      "shareCount": 2,
      "groupingConfidence": "high",
      "shares": []
    }
  ]
}
```

产品记录中的 `shares[]` 保存完整份额字段，保证前端展开后不需要再次请求。产品总数是本系统规则归并结果，不宣称等于官方统计。

## 归并规则

采用保守归并。处理顺序如下：

1. 规范化空格、全半角括号和大小写，但保留具有经济含义的词。
2. 仅移除明确位于名称末尾的份额标记，如 A、C、E、Y、人民币、美元现汇和美元现钞。
3. 使用规范化主名称与基金类型构成产品键。
4. 只有规则明确且同组不存在冲突时才合并。
5. ETF、ETF联接、LOF、发起式、定期开放期限、持有期、币种与对冲属性均作为产品身份的一部分，不被模糊删除。
6. 规则不明确或组内类型冲突时，一代码一产品，标记为低置信度。

不得仅凭编辑距离、模糊相似度或大模型判断自动合并生产数据。后续若接入官方主基金标识，官方映射优先于名称规则，并保留映射来源。

## 代表份额

产品列表的净值、涨跌幅、申赎状态取代表份额：

1. A 类；
2. 无 A 类时取人民币默认份额；
3. 无人民币默认份额时取 C 类；
4. 再按明确份额优先级与六位代码升序选取。

产品卡必须显示“代表份额：A类（000001）”，避免用户误以为指标属于整个产品。展开后每个份额独立显示代码、净值、涨跌幅、申赎状态和净值日期。

## 前端行为

- 默认视图为基金产品。
- 顶部显示“基金产品 X 只｜基金份额 Y 个”，并提供口径说明。
- 产品列表支持卡片和表格，但展开交互在两种视图中保持一致。
- 点击产品行或“查看份额”展开 `shares[]`。
- 搜索任一份额代码或名称时，返回所属产品并自动突出对应份额；搜索产品名称时返回产品。
- 分类和排序默认基于产品代表份额；展开列表不改变产品排序。
- 暂不增加“全部份额”作为默认页，可保留一个明确的口径切换入口供专业用户查看。

## 兼容与缓存

- `funds_active.json` 继续生成，并保留全部旧字段。
- 新前端优先读取 `fund_products.json`；若文件不可用，降级到 `funds_active.json` 并在浏览器端一代码一产品展示，不做高风险临时归并。
- 本地缓存增加 `schemaVersion`。旧缓存缺少版本时自动失效并重新获取，不尝试原地猜测迁移。
- 自动更新工作流同时提交 `funds_active.json`、`fund_products.json`、`funds_grouping_review.json` 和现有隔离文件。

## 质量审计

新增 `funds_grouping_review.json`，至少包含：

- 低置信度记录；
- 类型冲突组；
- 同一产品出现多个同名份额类别；
- 归并前份额数、归并后产品数和归并率；
- 各归并规则命中数量；
- 与上次更新相比产品数和份额数的异常变化。

自动化门槛：

- 每个活跃份额必须且只能属于一个产品；
- `productId + code` 关系唯一；
- 产品的 `shareCount` 等于 `shares.length`；
- 代表份额必须包含在 `shares[]` 中；
- 日更时产品数或份额数出现超阈值变化则失败，不覆盖上一版文件；
- 低置信度记录可以发布，但必须进入待核验清单。

## 测试策略

### Python

- 份额后缀识别的参数化测试；
- ETF/ETF联接、发起式、定开和持有期不可误合并测试；
- 稳定 `productId` 测试；
- 类型冲突降级测试；
- 代表份额优先级测试；
- 产品与份额完整性测试。

### JavaScript

- 新旧 JSON 兼容归一化测试；
- 产品、份额代码和名称搜索测试；
- 分类、排序与代表份额测试；
- 缓存版本失效测试。

### 端到端

- 默认显示产品总数和份额总数；
- 展开产品查看全部份额；
- 搜索 C 类代码定位产品并突出 C 类；
- 产品数据失败时安全降级；
- 移动端展开与键盘操作可用。

## 发布策略

1. 先在分支生成产品文件并产出质量审计报告。
2. 人工抽查黄金、半导体、AI、红利和债券五个主题中的典型多份额基金。
3. Preview 验证数量、搜索、展开和移动端。
4. 合并后由现有日更工作流生成生产数据。
5. 首周监控归并率、低置信度数量和产品数日变化，不以“接近官方数字”作为牺牲准确率的目标。

## 成功标准

- 用户默认看到产品级列表，且可展开查看全部份额。
- 任一现有六位代码仍能搜索到。
- 归并规则不会把已列出的不同经济属性产品合并。
- 产品数与份额数同时透明展示，官方口径差异得到解释。
- 每次日更可重复生成稳定产品 ID，并通过完整性校验。
